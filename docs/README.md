## 文書の役割と読み方

- **ユーザー確定事項**: `requirements.md` のR番号を参照します。整理や実装の都合で要件を変更しません。
- **設計判断**: ADRに理由を記録し、`architecture.md` と `plans/inori.md` に現在の境界・全体方針を反映します。
  ADR 0002には将来案も含まれるため、実装範囲はADR 0003以降と実装状況で確認します。
- **仮目標**: 要件表のT番号です。測定結果・合格条件と区別し、未測定の値を実績として扱いません。
- **作業上の仮定・提案**: 作業計画に明記します。優先順の提案だけで新しいユーザー要件や設計判断を確定しません。
- **実装状況**: 実装済み・検証済み・未検証を分けます。CI定義やテストコードの存在は、実行成功の証拠にしません。
- **検証記録**: 使用した構成・ハードウェア・ビルド・エンジン状態・時間・結果・未実施範囲を残します。
  現在の実装へ過去の測定値をそのまま当てはめません。
- **公開通信型**: `contracts/v1.json` を編集して `python tools/generate_contracts.py` を実行します。
  生成Rust/TypeScriptを独立に編集しません。

文書間に食い違いがある場合は、確定要件を維持し、判断の経緯と検証条件を照合して直します。
新しい文書や後の日付であることだけを理由に、要件や確認範囲を上書きしません。

## 更新する場所

| 変更 | 更新する文書 |
|---|---|
| ユーザーによる要件の追加・変更 | 要件表、統合プラン、関連ADR・受け入れ表 |
| 責務・依存方向・設計判断の変更 | 関連ADR、アーキテクチャ、統合プラン、実装状況 |
| 実装・検証の進展 | 実装状況、受け入れ表、関連するゲート・検証記録 |
| 作業の着手・完了・優先順の変更 | 次に行うこと。全体方針が変わる場合は統合プランも更新 |
| 起動・設定・配布コマンドの変更 | セットアップ、quickstart、構成手順など該当する手順書 |

実会話・録音・トークン・モデル重み・DB・実行ログはGitに置きません。
合成データのローカル検証は `.cache` を使い、文書には必要な条件と結果だけを記録します。
