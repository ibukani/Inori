# ADR 0003: サーバー構成の実装

状態: 採用・実装。日付: 2026-11-06。対象: R01–R05, R07–R11, R13–R16。
ADR 0002の採用方針を具体化する。GPUI適合性の採否とは分ける。

## 決定

`module-api` にIOに依存しない能力の型とライフサイクルを置き、`composition` に純粋な構成検証を置く。
起動元の `server::bootstrap` だけが標準モジュールを参照・生成する。
実行核は標準実装への依存を持たず、能力のtraitを呼び出す。
初期は能力の提供元を一つに限定する。複数の推論モデルは `inference.providers` 内の共通ルーターで選ぶ。
既存の `active_provider` とモデル切替のrevision・チェックポイントを維持する。

標準実装は9 crate（認識、対話、記憶、自律、推論、認識音声、合成音声、操作配送、標準接続）。
HTTPのルート登録・認証・管理はホストの責務とし、`channel.standard` は共通要求への変換・能力交渉を担当する。
標準接続を無効にしても管理のHTTPは残す。機能ルートは権限検査後に503を返す。
任意のクライアント名やGPUI型をサーバーに持たせない。

モジュールへ渡す情報は実行核が公開範囲で選ぶ。記憶の候補・推論入力を戻し、確定は実行核が行う。
Repositoryを渡さず、固有状態のCAS保存だけを自分のID・形式版に固定した `ModuleHost` で提供する。
拡張への権限確認口も検査専用とし、権限設定へのアクセスは渡さない。

構成の依存不足・循環・未知ID・契約版・排他競合・設定スキーマを静的検証する。
依存順の準備完了まで要求を受け付けず、失敗時は準備済み部分を逆順に終了する。
終了時は新規処理と状態保存を止め、中断して逆順に終了する。サーバー全体の終了待ちは5秒。
モジュールの同時数・推論の同時数・既存の有限キューで処理量を制限する。
背景抽出と自律推論の予算・排他を共有し、期限切れデータの保守は別のワーカーで動かす。

DB形式3に構成履歴と固有状態を追加する。人格revisionとは独立する。
無効化では状態を消さず、未知の形式版を初期化しない。
旧DBの更新前にサーバーロックと旧形式バックアップを必須にする。
バックアップCLIはread-only接続からコピーを作り、移行を行わない。

## 互換性とトレードオフ

composition省略は旧設定から明示した構成へ展開する。音声はURLを設定したものだけ有効にする。
新クライアントはHTTPとhelloで能力を確認し、旧クライアントのv1経路も維持する。
機能申告を権限には使わない。対話なしでも履歴・設定・手動の記憶管理を利用する。

ネイティブのモジュール追加には再ビルドが必要。設定による差し替えは登録済み実装の範囲で行う。
Rustのtraitを第三者向け安定ABIとして公開しない。既存のJSON-RPC拡張とSDKは継続する。
同一プロセスの標準モジュールは信頼するコードであり、OS隔離やRust panicからの生存は保証しない。
無停止更新、GUI構成エディター、新しい第三者判断SDK、高度な成長・感情・Live2Dは後続。

## 証拠

構成・保護・互換性は `apps/server/tests/composition.rs`、旧DBは
`crates/storage-sqlite/tests/migration.rs`、クライアントの開始抑止はclient-coreのテストで検査する。
既存の訂正・削除・公開範囲・モデル交換・Unknown操作・再生確認のテストを維持する。
測定・実行結果と未検証事項は `docs/development/status.md` を参照する。
