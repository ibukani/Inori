# Inori 統合実装プラン

この文書と requirements.md を現在の正本とする。会話での旧案を重複して採用しない。
ユーザー確定事項と仮目標は requirements.md に分離してある。

## 目的

基本人格を保ち、自分との交流を通して理解・思い出・距離感が育つ自律キャラクターを作る。
常時稼働する自宅Rustサーバーを状態の保存元とし、Windows GPUIクライアントは画面・音声を担当する。
AIはクラウド、別PC、Macなどに配置でき、特定モデルやSDKを人格へ埋め込まない。

## Windowsクライアントの方針

ユーザー確定事項（R17）: アプリ実行時の負荷とメモリ使用量の抑制を重視し、GPUIで継続開発する。
ユーザー確定事項（R18/R19）: クライアントは白と空色を基調にした単一時系列のチャット専用画面とする。
画像・キャラクター描画、記憶・人格・モデル・拡張権限の管理画面を置かず、接続設定を残す。
マイク入力とAI音声出力は独立トグルで、起動時は両方OFF。音声入力は明示ON時に発話を自動区切りする。
ウィンドウをトレイへ隠している間は音声会話を続け、トレイからミュートできる。終了操作では停止する。
AI管理アプリは別の将来作業とし、サーバーの人格・記憶・権限機能は維持する。
Tauriへの移行・比較試作は現行計画に含めない。

設計方針: 音声はclient-coreで有界メモリ上に取り込み、局所VADで区切ったWAVだけを既存の文字起こしAPIへ送る。
再生音を参照したエコー除去を行い、発話検出で再生・生成を中断する。音声をローカルファイルへ保存しない。
不要な再描画・ポーリング、履歴表示やキャッシュの保持量を見直す。これらは今後の最適化方針であり、実装完了を意味しない。
人格・記憶・自律活動は引き続きサーバーが所有し、GPUI依存はクライアント内に限定する。

仮目標T03のクライアント300MB・実行核200MBは維持する。対象8GB・内蔵GPUでの適合性、
他UI方式との負荷・メモリの優劣、長時間常駐時の安定性は未検証。
GPUIの選定は実機検証の合格を意味せず、[採用ゲート](../development/gpui-gate.md)を満たすまで試作として扱う。
詳細は [ADR 0004](../adr/0004-gpui-resource-priority.md) を参照する。

## 境界

- domain: 人格、原記録、記憶、権限、操作状態の検証。GUI/DB/HTTP非依存。
- runtime: 状態と保護規則、会話優先、中断、予算、操作台帳、記憶の確定。外部I/Oはports経由。
- module-api / composition: 能力の共通trait、定義、構成の静的検証と接続順。
- modules: 認識・対話・記憶整理・自律判断・推論・音声・操作配送・標準接続の独立Rust crate。
- storage-sqlite: 永続化、移行、楽観的なrevision検査、削除抑止、バックアップ。
- protocol: canonical JSON Schemaから生成するRust/TypeScriptの通信型。
- client-core: TLS接続、状態同期、音声、世代ごとの中断。人格を複製しない。
- extension-host/sdk: version付きJSON-RPC、能力宣言、権限、サイズ・時間・待ち行列の上限。
- desktop-gpui: 日本語チャット、音声トグル、接続設定、トレイ。管理画面・画像表示を含めず、GPUI依存をこの層へ限定する。

## 記憶と会話

原記録とAIの解釈を分離する。AIは推測と要約のみ提案し、確認済み情報や基本人格を直接上書きしない。
推測には出典、モデル、処理バージョン、期限、公開範囲を保存する。
訂正・削除はrevisionを検査し、旧出典からの自動再登録を抑止する。
モデル切替前の状態を記録し、再評価は変更案として取り扱う。モデル呼分けのたびに全履歴を処理しない。
公開用セッションにはprivate記憶を渡さない。未設定クラウドへ自動転送しない。

短い自然な文単位で生成・合成・再生を重ねる。記憶整理は返答の経路から分離する。
発話IDと生成IDを用い、中断後の古い結果と未再生の発話を排除する。
雑談、深い相談、操作の進行で応答方針を変え、LLMによる事前分類を毎回要求しない。
将来の音声直接入出力や画像入力を、初期STT→LLM→TTS構成に固定しない。

## 自律活動と拡張

不在時は興味・日課・振り返り・継続作業を扱う。自律方針は交換可能にする。
予定、実行結果、創作を区別する。推論・行動・料金の上限を設定し、会話を優先する。
モデル素材と描画エンジンを分離する。外部rendererは独立プロセス/ウィンドウとIPCで接続できる。
外部操作には操作IDを用いる。切断後に結果が不明な副作用を盲目的に再実行しない。

## 実装順

1. 正本・要件ID・ADR、workspace、公開契約、CI。
2. GPUI/音声の適合性検証。重大な未解決問題があればUI本実装を止め、測定結果を提示する。
3. 模擬AIと仮想時刻で人格・記憶・自律活動・権限・再起動を検証する。
4. Ollama/互換HTTP、whisper.cpp/VOICEVOX、GPUIチャット画面と音声会話を接続する。
5. モデル交換、異常終了、切断、移行・復旧、24時間稼働を検証する。

## 受け入れ条件

モデル交換で確認済み情報が失われず、古い背景処理が訂正を上書きしない。
削除が再要約から復活しない。古い音声を再生せず未再生部分を会話済みにしない。
結果不明の操作を無条件に繰り返さず、private記憶を公開会話へ混ぜない。
公開SDKだけで拡張を追加でき、queueとメモリが際限なく増えない。
Windows/macOSのサーバーをCIでビルドし、GUI依存を検査する。

## 採用・実装したモジュール構成

RE ENGINEを参考に、能力と実装の組み合わせを構成として保存・検証する案を
[ADR 0002](../adr/0002-module-composition-proposal.md) に記録した。
サーバー機能を組み替える方式を採用し、既存の標準機能を独立crateへ移行した。
初回は既存の標準サーバー機能をまとめて移し、設定ファイルと再起動で組み替える。新しい第三者判断モジュールSDKは次段階とする。
クライアントを通常のアプリとして保守し、クライアント側のモジュール登録・依存解決は対象から外す。
共通HTTP/WebSocketを使うアプリには標準接続を利用し、専用の変換が必要な接続先にはサーバー側アダプターを追加する。
人格・記憶・自律活動は全クライアントで共通とし、クライアントごとの判断核を作らない。

構成は `schema_version / enabled / bindings / settings` を持ち、起動前に検証する。
既存設定にcompositionがなければ従来相当へ展開し、既存のモデル選択を維持する。
依存順で準備し、準備完了後に要求を開始する。停止は中断後に逆順、サーバー全体で5秒まで待つ。
構成履歴・版付きモジュール状態は人格revisionから分離し、無効化では削除しない。
DB形式の追加移行は停止・ロック・旧形式バックアップ後に行う。バックアップ単独では移行しない。
管理API・保守は対話と標準接続を外しても継続する。

`validate-config`、認証済み `/v1/capabilities`、管理用 `/v1/modules`、
任意の `client.hello / server.hello` を追加する。未交渉のv1も引き継ぐ。
無効機能は認証・権限確認後に503 `module_unavailable` とし、副作用を開始しない。
画面は能力の可否を表示し、無効な対話や音声を開始しない。

詳細は [ADR 0003](../adr/0003-server-module-implementation.md)、
[構成の設定手順](../development/composition.md)、[検証状況](../development/status.md) を参照する。
新しい第三者判断SDK、専用外部サービス接続、GUI構成エディター、無停止差し替えは次段階。
元の成長・感情・Live2D・実音声・GPUI採用ゲートと長期運用の後続計画を維持する。
